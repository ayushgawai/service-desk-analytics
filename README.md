# Service Desk Analytics

SLA and client health analytics over support tickets: dbt models, SLA breach
prediction, A/B analysis and a dashboard. All synthetic, runs on a laptop with
DuckDB — no cloud needed.

## Design

```
 src/gen.py          src/main.py (load)        dbt/ (DuckDB)            outputs
┌──────────────┐    ┌───────────────┐    ┌──────────────────────┐    ┌────────────────────┐
│ 150 accounts │    │ raw_accounts  │    │ stg_*  (SLA logic in │    │ reports/dashboard  │
│ 180 days of  ├───►│ raw_tickets   ├───►│  stg_tickets)        ├───►│  .html + Tableau   │
│ tickets +    │CSV │ raw_policies  │    │ fct_tickets          │    │  CSV extracts      │
│ uptime checks│    │ raw_uptime    │    │ agg_account_day      │    ├────────────────────┤
└──────────────┘    └───────────────┘    │ agg_client_health    │    │ src/predict.py AUC │
        ▲                                └──────────────────────┘    │ src/ab.py bootstrap│
        └── staffing A/B injected day 120 (treatment accounts)       └────────────────────┘
```

| Layer | Choice | Why |
|---|---|---|
| Warehouse | DuckDB file (`warehouse.duckdb`) | Real SQL/dbt, zero infra; swap profile for BigQuery/Snowflake later |
| Transform | dbt staging → facts → aggregates | Tested, documented models; SLA logic in one place (`stg_tickets`) |
| Generator | NumPy/pandas, seeded | Deterministic; treatment effect + breach signal are known ground truth |
| Prediction | HistGradientBoosting, creation-time features only | No leakage; time-based holdout mirrors production scoring |
| A/B | Per-account breach rates, cluster bootstrap (1000×) | Tickets within an account are not independent |
| Dashboard | Generated HTML + Tableau-ready CSVs | Tableau isn't laptop-runnable; same marts feed both (see Limitations) |

KPI definitions (attainment, breach, FRT, backlog, health band): **docs/kpis.md** —
dashboard, dbt and reports all use those exact definitions.
One-page recommendations: `reports/recommendation_prediction.md`,
`reports/recommendation_staffing.md` (regenerated by every bench run).

## Run / test / bench

```bash
python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest tests -q                      # 5 passed
.venv/bin/python src/main.py bench --tickets 120000      # gen + dbt + predict + A/B + dashboard
.venv/bin/python src/main.py all --tickets 1200000       # full 1.2M-ticket scale (same code path)
dbt run  --project-dir dbt --profiles-dir dbt            # models only (needs load first via bench/all)
dbt test --project-dir dbt --profiles-dir dbt            # dbt schema tests
```

Individual steps: `gen | load | dbt | predict | ab | dashboard` (see `src/main.py`).

## Limitations (honest)

- **Synthetic data only.** The 0.857 AUC and −7.8pp A/B effect measure the
  pipeline against *injected* ground truth, not real-world performance. On real
  tickets expect lower AUC; the time-holdout + leakage-free features are the
  parts designed to carry over.
- **Tableau** is not run locally (no licence/server on a laptop). The deliverable
  is the two Tableau-ready extracts plus an HTML dashboard built from the same
  dbt marts, so numbers match by construction.
- **Backlog** is an end-of-day approximation from created/resolved dates, not a
  true open-ticket snapshot — that needs hourly state history (docs/kpis.md).
- All tickets are `closed`; open-ticket ageing/censoring is not modelled.
- dbt models are views on DuckDB; no incremental models, snapshots or CI yet.
- `dbt test` was not executed in the build sandbox (CLI approval); schema tests
  are defined in `dbt/models/schema.yml` and `dbt run` passes 8/8 models.
